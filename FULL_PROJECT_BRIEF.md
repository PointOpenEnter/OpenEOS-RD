## 0. Кто пользователь и зачем это нужно

- Пользователь — **не программист**. Прямая цитата: «я не программист, а все равно должен следить и во всем разбираться» — это НЕ должно быть так; вся ответственность за корректность кода, бэкапов и истории изменений лежит на агенте, не на пользователе.
- Проект для **личного использования**: пользователь читает пробег (shutter count) своих камер **перед продажей**. Программа **не будет распространяться или продаваться**.
- **Жёсткое правило безопасности (абсолютный приоритет, ЗАФИКСИРОВАНО в AGENTS.md Rule 1)**: НИКОГДА не выполнять операции записи в камеру, ничего, что могло бы её повредить. Любая функция — только чтение.
- Пользователя интересует прежде всего **механический** счётчик (а не электронный/суммарный).
- Исследуем Торнадо (Tornado EOS). У пользователя есть доступ к дампам Wireshark (`.pcapng`) из сессий Tornado — это единственный источник протокольных данных, которые мы анализируем.
- Общая цель: добиться **рабочего чтения показаний счётчика по USB** для как можно большей части линейки Canon (в идеале — для всей линейки), не покупая по дампу Tornado на каждую отдельную камеру.

## 3. Два независимых метода чтения счётчика — и их реальный статус

### 3.1. EXIF/метаданные (стабильное, production-ready ядро — создано до текущей сессии)

Через ExifTool (постоянная сессия `-stay_open` для пакетной скорости) читает:
- Canon CR3 (DIGIC X): `Track4:ShutterCount` из QuickTime/ISOBMFF-контейнера — работает для EOS R5, R6, R6 Mark II, R3, R7, R8, R10, R50, R100, 1D X Mark III.
- Nikon NEF (DSLR и Z-серия): тег `MakerNotes:ShutterCount` (`0x00a7`) — Z9/Z8/Z7(ii)/Z6(ii)/Z5/Zf, D850/D780/D750/D500/D6/D5/D4.
- Sony ARW (A1, A9-серия, A7R-серия, A7-серия, A6xxx).
- Fujifilm RAF, универсальный DNG.

**Принципиальное ограничение (НЕ баг, а аппаратный факт)**: этот метод **в принципе не работает** для Canon-камер, которые физически не записывают счётчик в файл снимка — это все зеркальные/беззеркальные камеры DIGIC-8-и-старше:
- Canon EOS R (2018), EOS RP, EOS M50, EOS 250D, EOS 90D — беззеркальные без `Track4`.
- Canon DSLR: 5D Mark IV, 5D Mark III, 6D Mark II, 80D — счётчик только во внутренней EEPROM тушки.

Именно этот пробел и закрывает USB-PTP-метод (раздел 3.3) — это ключевая мотивация всей работы с протоколом.

### 3.2. SD-карта / CHDK CamInfo_Debug (добавлено в текущей сессии, ПРИЗНАНО НЕРАБОЧИМ на реальных камерах пользователя)

Идея (из внешнего открытого проекта `github.com/fedoroff-aa/shutter-check-canon`, сверено байт-в-байт): кладём на карту два файла —
- `extend.m`:
  ```
  private sub Initialize()
  System.Create()
  CamInfo_Debug(1)
  end sub
  ```
- `script.req`: `for DC_scriptdisk`

...плюс отметку CHDK boot-sector marker: ASCII `"SCRIPT"` (6 байт, без NUL) по смещению `0x1F0` boot-сектора раздела карты. **Независимо проверено по первоисточнику** (официальная CHDK-вики, страница `Canon_Basic/Card_Setup`) двумя способами (прямое чтение вики + `dd bs=1 count=6 seek=496`, где 496=0x1F0) — спецификация подтверждена, НЕ выдумана.

На камере: режим Play + многократные нажатия SET должны запустить скрипт; результат — файл типа `CAM_INFO.XML` в корне карты.

**Реализовано в `cbasic_card.py`** (полностью нативно, без внешнего EOScard.exe, который несколько антивирусов определяли как вредоносный):
- `write_script_marker(drive)` — сырые Win32-вызовы (`CreateFileW`/`ReadFile`/`WriteFile`/`SetFilePointer`/`CloseHandle`) на `\\.\<буква>:`, проверка сигнатуры boot-сектора `0x55 0xAA` на смещении `0x1FE` перед записью. Добавлен retry-цикл (5 попыток × 0.4с) — после `format.com` Windows ещё домонтирует том, и `CreateFileW` может на мгновение вернуть `ERROR_ACCESS_DENIED`.
- `format_card(drive, volume_label="OPENEOS")` — `format <буква>: /FS:FAT32 /Q /V:<метка> /X /Y` через `subprocess.run`, с предварительной проверкой `exceeds_fat32_limit`.
- `prepare_card(drive)` — метка + копирование файлов + та же проверка лимита.
- `format_and_prepare_card(drive, volume_label="OPENEOS")` — единая кнопка «сделал всё»: формат → повторный скан дисков (с тем же retry-паттерном 5×0.4с, т.к. `GetVolumeInformationW` тоже может на миг не увидеть только что отформатированный диск) → `prepare_card`.
- **Ограничение ≤32 ГБ / FAT32** добавлено явно (константа `MAX_CARD_SIZE_BYTES = 32 * 1024**3`, свойство `RemovableDrive.exceeds_fat32_limit`, визуальная пометка `"⚠ >32 ГБ, не подходит"` в UI) — FAT32 штатно не поддерживает разделы больше 32 ГБ.
- Удалена ссылка `EOSCARD_INFO_URL` (была латентным багом — переменная использовалась в `openeos_service.py`, но нигде не определялась в реальном `cbasic_card.py`, клик бросил бы `AttributeError`).
- В GUI (`openeos_service.py`, вкладка «Карта»): кнопка «Записать файлы на карту» заменена на «Форматировать и подготовить карту» (`on_card_format`) — с явным подтверждением (`messagebox.askyesno`, предупреждение о полном стирании карты) и ранней проверкой лимита 32 ГБ/FAT32 с понятным сообщением пользователю. Все новые элементы UI снабжены всплывающими подсказками (`attach_tip()` — новый вспомогательный метод, навешивает `InfoToolTip` с кастомным текстом/заголовком).

**РЕАЛЬНЫЙ РЕЗУЛЬТАТ ТЕСТА ПОЛЬЗОВАТЕЛЯ (это финальный вердикт по этому методу)**: карта читается камерой (мигает индикатор доступа), НО **файл результата никогда не появляется**, сколько бы раз ни нажимали SET — ни на Canon EOS R6 Mark II, ни на EOS R10. Прямая цитата пользователя: «карточный метод меня не интересует, я уже знаю что на р6 это может сработать. МНЕ ВАЖНО сделать рабочее чтение с камеры [по USB]».

Вероятная (НЕподтверждённая, это моя собственная гипотеза, не факт) причина: референсный автор `shutter-check-canon` лично подтвердил метод только на базовой/не-Mark Canon EOS R; другие R-модели указаны как «подходящие» лишь предположительно (не тестировались им самим). Возможно, новые прошивки DIGIC X убрали/изменили путь триггера Play→SET, который работал на базовой R6.

**Статус метода: реализован полностью, но практически НЕ ПРИГОДЕН для реальных камер пользователя. Понижен пользователем в приоритете. Не тратить время на доработку, если явно не попросят.**

### 3.3. USB-PTP прямое чтение (ОСНОВНОЙ, самый важный рабочий метод — найден и реализован до и во время текущей сессии)

Это то, что реально важно пользователю: «МНЕ ВАЖНО сделать рабочее чтение с камеры».

**Транспорт**: Windows WPD (Windows Portable Devices) / MTP pass-through — стандартный драйвер Windows, замена драйвера не нужна. Реализовано через COM-интероп (`IPortableDeviceManager`, `IPortableDevice`, `IPortableDeviceValues`, `IPortableDevicePropVariantCollection`) в `eos_probe.cs` / `canon_live_usb.cs`.

**Ключевые PTP vendor-опкоды Canon**:
- `0x1001` — стандартный GetDeviceInfo (PTP-стандарт).
- `0x9114`/`0x9115` — SetRemoteMode/SetEventMode (инициализация сессии, зеркалит EDSDK).
- `0x9116` — Canon GetEvent.
- `0x911B` — SetUILock.
- `0x905C` — обмен аутентификационными токенами (см. ниже).
- `0x9052`/`0x9053` — MonRead-канал текстовых команд к **отдельному микроконтроллеру Toshiba TX19A MPU** (НЕ главный процессор DryOS!) — несёт команды `MonOpen`/`MonClose`/`MonReadAndGetData`, **не требует ключа авторизации для чтения**.

**Служебная команда `FA_GetProperty`** (авторизованный путь) читает внутренние свойства Canon:
- `0x12000001` — механический счётчик затвора (то, что важнее всего пользователю).
- `0x12000003` — суммарный/общий счётчик затвора.
- `0x12000005` — счётчик включений + наработка.
- `0x13000000` — журнал ошибок.

**Устаревшее свойство `0xD1AC`** (`PTP_DPC_CANON_EOS_ShutterCounter`) работало на DIGIC5-и-старше (5D Mark III), но **удалено** (возвращает `0x2005 OperationNotSupported`) начиная с DIGIC6.

**Полная подтверждённая последовательность протокола** (извлечена из дампов Tornado, задокументирована в проектных claude.ai-доках `live_read_success_2026-11-04.md`/`analysis_2026-11-04.md`):
```
GetDeviceInfo
→ 0x9114(1)
→ 0x9115(1)
→ 0x9116
→ 0x905C × 3   (обмен токенами аутентификации)
→ подготовительные вызовы:
    FA_GetProperty 0x2
    FA_TurnOffDisplay
    IsFactoryMode
    FA_GetProperty 0x0100001D
    0x911B SetUILock
    FA_GetProperty 0x01000006, 0x02000005, 0x80030000
    (таймированные паузы ~1с / 0.84с / 0.31с — важны, без них камера может зависнуть/ошибиться)
→ FA_GetProperty 0x12000001  (механический счётчик)
→ FA_GetProperty 0x12000003  (суммарный счётчик)
→ FA_GetProperty 0x13000000  (журнал ошибок)
→ FA_GetProperty 0x12000005  (включения + наработка)
```
Формат записи журнала ошибок: 16 байт на запись — u32 время, u16 lensID, 2 байта паддинга, u16 код ошибки, 2 байта паддинга, u32 суммарный счётчик. Код 67 = Err60, 101 = Err70.

**Аутентификационные токены**: пара `Token2`/`Token3` (по 32 бита каждый), отправляются через `0x905C` как часть фиксированной 39-байтовой структуры `AuthPayload`:
```
ASCII "saitamatch" (10 байт) + NUL + u32(1) + u32(2) + token(u32, little-endian) + 16 нулевых байт
```
Токены **жёстко привязаны в коде** к точным парам (строка модели, строка-хэш серийника `PtpSerial`) через класс/массив `CamProfile` — это и есть предохранитель (`Guard()`), не дающий отправить неверный токен на непроверенную камеру (исторически приводило к тому, что камера на уровне PTP принимала (неверный) токен (`0x2001`), но затем зависала/ошибалась (`Err 70`) на последующем вызове `FA_GetProperty` — это произошло на EOS R10 (первая попытка) и на EOS R6 Mark III).

**Важный нюанс**: поле `PtpSerial` — это НЕ буквальный серийный номер камеры, а 32-символьный hex-хэш серийника (например, `"52158238494bd8c1b20eceb348b72a00"` для R6 Mark II пользователя, `"a52fcb39b240a529a9b621b771e6d456"` для его R10). Точный алгоритм хэширования **неизвестен/не подтверждён**, предположительно это собственный ID-строки от WPD.

**Текущие известные профили (ровно то, что в коде `eos_probe.cs` сейчас, ничего не придумано)**:
```csharp
class CamProfile { public string Model; public string PtpSerial; public uint Token2; public uint Token3; public string Source; }
static readonly CamProfile[] Profiles = {
    new CamProfile { Model = "Canon EOS R6m2", PtpSerial = "52158238494bd8c1b20eceb348b72a00", Token2 = 0x00071590, Token3 = 0x00150AD3, Source = "р62.pcapng / R6m2_live.pcapng" },
    new CamProfile { Model = "Canon EOS R10",  PtpSerial = "a52fcb39b240a529a9b621b771e6d456", Token2 = 0x00074218, Token3 = 0x01C2D2D2, Source = "р10.pcapng" },
};
```

**Guard() — центральный белый список разрешённых команд** в `eos_probe.cs`: разрешает только `0x1001`/`0x9116`/`0x9114`/`0x9115`/`0x9053` без данных (чтения), `0x905C` с данными, совпадающими с `Auth1` или `AuthPayload(Active.Token2)`/`AuthPayload(Active.Token3)` (только если `Active != null`), `0x9052` с `MonOpenP()`/`MonCloseP()`/`IsAllowedMonRead(...)` или константами `TurnOffDisplay`/`IsFactoryMode`, или любой `FaGetProperty(p)` для `p` из `AllowedProps`, и `0x911B` без данных. Всё остальное бросает исключение и логируется как `"GUARD BLOCKED op=0x{0:X4} len={1}"`. Если модель/серийник не совпали ни с одним известным профилем — исключение `"Модель {di.Model} не проверена. Служебные запросы не отправлялись, камера в безопасности."` — то есть **по умолчанию** код физически не может отправить служебные команды на незнакомую камеру.

**Подтверждённые реальные результаты (из проектных claude.ai доков и этой сессии)**:
- Первое успешное живое чтение на R6 Mark II — 2026-11-04, 18:03, через WPD MTP pass-through.
- R10: первая попытка — провал (`FA_GetProperty` зависал на 30с, `hr=0x802A0006`, камера автоотключалась); позже — успех, после добавления подготовительных шагов `0x9114`/`0x9115`/`0x9116` и правильных токенов.
- R6 Mark III: провал на `FA_GetProperty(0x12000001)` после ~6с, `hr=0x8007001F`, на камере `Err 70` — именно этот провал привёл к решению жёстко блокировать неподтверждённые модели в коде (Guard + Profiles).

**НОВОЕ в этой сессии — форензический факт о стабильности токенов**: написан и запущен скрипт `scan_tokens.py` (см. раздел 7), который по сырым байтам ищет маркер `"saitamatch"` в двух НЕЗАВИСИМЫХ файлах захвата (`R6m2_live.pcapng` и `R6m2_compare.pcapng`, оба — реальные сессии Tornado с одной и той же физической камерой пользователя). **Результат, проверенный напрямую**: `Token2=0x00071590` и `Token3=0x00150AD3` байт-в-байт идентичны во всех вхождениях — и между двумя разными сессиями захвата, и дважды внутри одного файла `R6m2_compare.pcapng`. Это **доказывает**, что токены — НЕ одноразовые/случайные challenge-значения сессии, а стабильная константа (как минимум) для этой конкретной камеры. Это прямой ответ на запрос пользователя «сверяй».

## 4. Эксперимент `--force-model-match` (реализовано в этой сессии, результат ЕЩЁ НЕ ПОЛУЧЕН)

**Контекст запроса пользователя**: пользователь сегодня (2026-11-05) планировал одолжить ещё 2 камеры — второй физический экземпляр Canon EOS R6 Mark II («р62», другой серийник, та же модель) и базовую/оригинальную EOS R6 («р6», другая модель). Цель — проверить, сработают ли уже известные реальные токены R6 Mark II на ДРУГОМ физическом экземпляре той же модели. Пользователь явно исключил карточный метод для этого теста и хочет именно USB.

Пользователь также явно спросил: стоит ли покупать ещё 2 дампа Tornado (~7000, валюта не уточнена) для этих двух конкретных камер, даст ли это «прорыв» или просто ещё пару ключей для ещё 2 конкретных камер (без возможности обобщения). Ответ (дан в сессии, остаётся верным): покупка новых дампов для конкретных камер **НЕ является масштабируемым прорывом сама по себе** — это просто добавляет ещё записи в таблицу `CamProfile`, по одной на физическую камеру/модель, а не выводит общую формулу. Пользователь сам это понял и сказал «ответь на вопрос и делай вариант Б» — вариант Б = бесплатный эксперимент ниже, без покупки нового дампа.

**Реализация (в `eos_probe.cs`, полностью опционально, НЕ меняет поведение по умолчанию)**:
- Добавлен флаг `--force-model-match` как третий CLI-аргумент.
- Если точного совпадения (модель + серийник-хэш) не найдено, но флаг передан — ищется совпадение ТОЛЬКО по модели (игнорируя серийник), и применяются известные токены R6 Mark II к ЛЮБОМУ R6 Mark II независимо от серийника.
- Если камера ответит `Err 70`/зависанием — это и будет ответ: токен привязан к конкретному экземпляру, а не к модели.
- Без флага поведение **полностью идентично прежнему** (безопасно по умолчанию).

**Точный код изменений в `eos_probe.cs`** (для справки, ничего не придумано):
```csharp
// в Main(string[] args), сразу после разбора mode/LogPath:
bool forceModelMatch = args.Length > 2 && args[2] == "--force-model-match";
Log("=== eos_probe mode=" + mode + " === build=v7-mon" + (forceModelMatch ? " [ЭКСПЕРИМЕНТ: --force-model-match]" : ""));

// в ветке режима "counters", сразу после разбора device_info:
foreach (CamProfile pr in Profiles)
    if (pr.Model == di.Model && pr.PtpSerial == di.Serial) Active = pr;
if (Active != null) Log("Profile: " + Active.Model + " (tokens from " + Active.Source + ", exact serial match)");
if (Active == null && forceModelMatch)
{
    foreach (CamProfile pr in Profiles)
        if (pr.Model == di.Model) { Active = pr; break; }
    if (Active != null)
        Log("ЭКСПЕРИМЕНТ: серийник " + di.Serial + " не совпал с " + Active.PtpSerial +
            " — применяю токены " + Active.Source + " по совпадению ТОЛЬКО модели. " +
            "Если камера ответит Err 70/зависанием — это и есть ответ: токен привязан к экземпляру, не к модели.");
}
if (Active == null)
    throw new Exception("Модель " + di.Model + " не проверена. Служебные запросы не отправлялись, камера в безопасности.");
```

**Новый файл**: `eos_probe_4_experiment_force_model.bat` — отдельный, изолированный entry point (сознательно НЕ смёржен со штатным `eos_probe_2_counters.bat`, чтобы не трогать безопасное поведение по умолчанию). Запрашивает явное подтверждение пользователя перед запуском, собирает `eos_probe.exe` через `csc.exe /platform:x86`, запускает `eos_probe.exe counters "" --force-model-match`, выводит результат и путь к логу.

**Важно**: этот эксперимент **применим только к R6 Mark II** (т.к. только для неё есть реальные токены). Для базовой EOS R6 («р6») токенов НЕТ ВООБЩЕ — её нельзя протестировать этим способом, только card-методом (который сам пользователь уже считает малоперспективным для современных тел, но по его словам «на р6 это может сработать», т.к. это ровно та модель, на которой автор `shutter-check-canon` лично подтвердил метод).

## 6. Прочие вспомогательные артефакты (не часть продукта, созданы для анализа в этой сессии)

- `/tmp/.../scratchpad/scan_tokens.py` — одноразовый форензический скрипт (НЕ часть проекта, не коммитился на устройство), ищет байтовый маркер `b"saitamatch"` в `.pcapng`-файлах и извлекает 39-байтовую структуру `AuthPayload` целиком, проверяя стабильность токена. Использовался на `R6m2_live.pcapng` и `R6m2_compare.pcapng` (оба временно стейджились в облако только для чтения, не менялись, не коммитились обратно — это постоянно живущие на устройстве референсные дампы).
  ```python
  import sys
  MARKER = b"saitamatch"
  def scan(path):
      with open(path, "rb") as f:
          data = f.read()
      hits = []
      start = 0
      while True:
          idx = data.find(MARKER, start)
          if idx == -1:
              break
          payload = data[idx:idx+39]
          if len(payload) == 39:
              token = int.from_bytes(payload[19:23], "little")
              tail_zeros = payload[23:39]
              hits.append((idx, token, tail_zeros == b"\x00"*16, payload.hex()))
          start = idx + 1
      return hits, len(data)
  ```

## 7. Антивирусные ложные срабатывания (обсуждалось, решение — НЕ трогать)

- `OpenEOS_Service.exe` (текущая сервисная часть): 1 детект из 69 движков (SecureAge, «Malicious»).
- Более ранний инструмент EOScard (теперь полностью заменённый нативным кодом в `cbasic_card.py`, см. раздел 3.2): 6 детектов из 69 — гораздо серьёзнее.
- Причина текущего единичного детекта — типичный ложноположительный паттерн для однофайловых сборок PyInstaller (`--onefile`): распаковываемый во временную папку при запуске единый exe-блоб + отсутствие цифровой подписи + несколько встроенных PE/DLL (`canon_live_usb.exe`, `eos_probe.exe`, `EDSDK.dll`, `EdsImage.dll`) структурно похожи на dropper/self-extracting-loader для статических эвристических движков (конкретно SecureAge/APEX), хотя ни один поведенческий движок (CrowdStrike, SentinelOne) не триггерится. Это известный, распространённый класс ложных срабатываний для PyInstaller onefile-сборок, не свидетельство реального вредоносного поведения.
- **Пользователь явно решил НЕ трогать структуру сборки**: «ладно, не будем трогать, пусть будет 1 ехе». Решение зафиксировано — не предлагать повторно без явного запроса.

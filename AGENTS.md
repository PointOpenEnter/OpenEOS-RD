# Инструкции для ИИ-агентов и разработчиков (AGENTS.md)

Этот документ является **обязательным сводом правил (конституцией проекта)** для любых систем искусственного интеллекта (Antigravity, Claude, ChatGPT, Cursor, Copilot) и разработчиков, вносящих изменения в кодовую базу **OpenEOS-RD**.

---

## 🛑 Главные нерушимые правила

### 1. Запрет на немотивированные правки проверенного кода
* **Никогда не переписывайте и не рефакторите работающий код**, если это прямо не запрошено пользователем.
* Логика ядра, интеграция ExifTool/Perl, функции нормализации тегов и база официальных ресурсов камер проверены на реальных файлах и признаны эталонными.
* Запрещено «наводить красоту», переименовывать рабочие переменные, переупорядочивать методы без технической необходимости.

### 2. Запрет на выдумывание (галлюцинации) протоколов и тегов
* **Запрещено придумывать несуществующие теги, формулы износа или процентные шкалы.**
* Пробег камеры — это объективное целое число из метаданных. Нельзя интерполировать, округлять или генерировать синтетические проценты «остатка ресурса», если производитель их не предоставляет.
* Любые теги должны строго сверяться с официальной спецификацией ExifTool (`Nikon.pm`, `Canon.pm`, `Sony.pm`) или техническими стандартами CIPA/ISO.

### 3. Сохранение зафиксированного дизайна (UI Constitution)
* **Размер окна строго фиксирован: `860 × 520 px` (`self.root.resizable(False, False)`).** Запрещено возвращать динамическое изменение размера или кнопку максимизации без прямого указания.
* **Никаких белых вспышек и фонов:** тёмный цвет `#1F1F1F` и DWM Dark Mode задаются синхронно в первую миллисекунду запуска.
* **Запрет на хаки скрытия окна (`withdraw` / `deiconify`):** в Windows 11 скрытие окна ломает очередь сообщений перерисовки GDI (`WM_PAINT`) и порождает неперерисованные белые прямоугольники.
* **Единый стиль карточки результатов:**
  * Заголовок: `ПОКАЗАНИЕ СЧЁТЧИКА ЗАТВОРА` (без знаков вопроса вверху).
  * Крупное число счётчика и статус.
  * Разделитель.
  * Три колонки: `КАМЕРА`, `ДАТА СЪЁМКИ`, `РЕСУРС ЗАТВОРА (?)`.
  * Интерактивная иконка `(?)` со справкой размещается **исключительно** справа внизу рядом с «РЕСУРС ЗАТВОРА (?)».

### 4. Не ломать смежный функционал
* Любое локальное изменение должно затрагивать **только обсуждаемую область**.
* Если меняется одна кнопка или подпись, запрещено менять упаковку соседних контейнеров, размеры шрифтов других блоков или конфигурацию вкладок.

### 5. Обязательный отчёт об изменениях
Каждый ответ агента после модификации кода обязан содержать:
1. **Точный список изменённых файлов.**
2. **Что конкретно изменено (до/после).**
3. **Обоснование:** почему именно такое изменение решает задачу и как подтверждено отсутствие регрессий.

### 6. Обязательный бэкап ПЕРЕД правкой (без исключений)
* **Перед ЛЮБОЙ правкой любого рабочего файла** (`.py`, `.bat`, `.cs` и т.д.) агент обязан сначала сохранить его текущее содержимое в `backup_ГГГГ-ММ-ДД/<имя_файла>.bak` (папка с сегодняшней датой; если правок за день несколько — существующий `.bak` не перезаписывается повторно, он уже содержит состояние "до первой правки за день") и только потом вносить изменения.
* Пользователь — не программист и не обязан отслеживать, какая копия файла актуальна, где она лежит и какая версия "правильная". Это обязанность агента, целиком и без перекладывания на пользователя.
* **Запрещено** редактировать файл "в уме"/в рабочей копии и сразу перезаписывать им файл пользователя без предварительного бэкапа — даже если изменение кажется небольшим.
* Каждое изменение, достойное отката назад, фиксируется записью в `CHANGELOG.md` (дата, что изменено, зачем) — это единственное место, где история изменений гарантированно не теряется при сжатии переписки с ИИ.
* Перед тем как править код, агент обязан убедиться, что редактирует ДЕЙСТВУЮЩУЮ копию на компьютере пользователя (через привязку устройства), а не случайную копию файла, оставшуюся в переписке/загрузках чата.

### 7. Переключение темы (светлая/тёмная) — сохранение состояния вкладок
* Тема при запуске всегда берётся из системной (`detect_system_theme()`) — это НЕ трогать без прямого запроса.
* `toggle_theme()` полностью уничтожает и заново создаёт ВСЕ виджеты окна (`create_interface()`), поэтому любое состояние, которое видно только на экране (текст в полях результата, включённые/отключённые кнопки, отображаемые данные), после переключения темы исчезает, если его явно не восстановить.
* Сами данные (например `self.card_last_data`, `self.usb_data`, значения `tk.StringVar`, прочитанные заранее в Python-переменные) при этом НЕ теряются — это обычные атрибуты объекта, а не виджеты.
* Поэтому: **у каждой вкладки, которая хранит «живое» состояние (результат чтения, статус подключения, введённый пользователем текст и т.п.), должно быть соответствующее восстановление внутри `toggle_theme()` после вызова `self.create_interface()`** — переотрисовать вкладку из уже имеющихся данных, НЕ запрашивая данные заново (не переподключаться к камере, не перечитывать файл с карты и т.д.). Текущие примеры такого восстановления — для вкладки «Проверить фото» (ярлыки/метаданные), «Камера по USB» (`self._on_connect_success(self.usb_data)`) и «Карта» (пересборка сводки из `self.card_last_data` + значение поля «Метка камеры») — см. `toggle_theme()`.
* **При добавлении новой вкладки, которая будет хранить результат/состояние, нужно сразу добавить для неё такой же блок восстановления в `toggle_theme()`** — иначе переключение темы будет выглядеть как потеря данных пользователем, хотя данные на самом деле никуда не делись.

## 🔒 Политика конфиденциальности данных (Data Hygiene)

**Категорически запрещено коммитить в репозиторий GitHub:**
* Любые оригинальные пользовательские снимки (`.CR2`, `.CR3`, `.NEF`, `.ARW`, `.DNG`, `.JPG`).
* Дампы сетевого трафика и USB-шины (`.pcap`, `.pcapng`).
* Серийные номера камер пользователей и персональные идентификаторы.
* Временные каталоги сборки (`build/`, `dist/`, `build_spec/`, `.spec`).
* Бинарные `.exe` файлы в основную ветку (готовые исполняемые файлы публикуются исключительно в секции [Releases](https://github.com/PointOpenEnter/OpenEOS-RD/releases)).

## 🏷 Регламент управления версиями (Versioning & Git Tags)

Проект строго следует принципу контрольных точек:

| Версия | Тип релиза | Назначение |
| :--- | :--- | :--- |
| **v0.3.1** | Исходный релиз | Первая базовая версия со светлой темой и сканером папок |
| **v0.3.2** | Patch | Исправления критических багов без смены интерфейса |
| **v0.4.0** | Minor | Внедрение тёмной темы Fluent и базы паспортных ресурсов |
| **v0.4.1** | Stable Patch | Устранение артефактов отрисовки, фиксированный размер, иконка камеры |
| **v0.4.2** | Patch | (тег уже стоит в репозитории; см. `CHANGELOG.md` за подробностями) |
| **v0.5.0** | Minor | Прямое чтение счётчиков по USB (PTP 0x905C), альтернативный метод через карту памяти (CamInfo_Debug), подробная диагностика и UI-доработки вкладок «Карта»/«USB» — присвоено стабильным 2026-11-05, подробности см. `CHANGELOG.md` |
| **v1.0.0** | Major | Завершённая стабильная версия с поддержкой USB PTP (план; не достигнута на момент v0.5.0) |

* Каждая принятая версия **обязательно маркируется Git-тегом** (например: `git tag -a v0.4.1 -m "Release v0.4.1"`).
* Любой разработчик должен иметь возможность переключиться на любой исторический тег и воспроизвести сборку.
* **v0.5.0 помечена в `CHANGELOG.md` и `APP_VERSION` (`openeos_service.py`), но Git-тег на неё нужно поставить вручную на устройстве** (у ИИ-агента в облачной сессии нет доступа к командной строке устройства, только к файлам): `git tag -a v0.5.0 -m "Release v0.5.0"` из папки проекта.
